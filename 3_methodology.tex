\section{Methodology}\label{method}

To test our hypotheses, we adopt a two-step methodology.
First, we gather descriptive statistics to quantify the prevalence, retention, 
and temporal trends of different license types within publicly available repositories.
We then identify projects that switched from permissive to restrictive 
licenses (or vice versa) and measure their performance changes before and after 
the switch, using a multivariate multiple regression approach.

\subsection{License Types}

We group licenses using the standard classification~\cite{kaminski2007open}:
\emph{Permissive} (e.g., MIT, BSD; minimal restrictions; can be bundled
with proprietary code~\cite{kapitsaki2019modeling,kapitsaki2022help});
\emph{Copyleft} (e.g., GPL; derivative works must share the same
license~\cite{d2007copyleft,laurent2012free});
\emph{Weak Copyleft} (e.g., LGPL, MPL; linking permitted, modifications
to the licensed components must stay
open~\cite{alamoudi2020open,gamalielsson2017licensing});
\emph{Conditional Open} (e.g., CC-BY/CC-BY-SA; attribution or
share-alike required~\cite{de2009creative}); and
\emph{Public Domain} (e.g., CC0, Unlicense; explicit waiver of
copyright). We treat \emph{no-license} projects (no LICENSE file at
all; default ``all rights reserved'') as a \emph{separate} category,
not part of public-domain: the legal effect is opposite.

Given 597 distinct licenses we manually classified the top 50,
covering 98.92\% of licensed projects; the remaining $\sim 1\%$ were grouped as
\emph{other}.

\subsection{World of Code Infrastructure}

We work with World of Code
(WoC)~\cite{ma2019world,ma2021world},\footnote{\url{https://worldofcode.org}}
which cross-references source-code change data across the FLOSS
ecosystem and provides maps connecting git objects (commits, blobs,
authors) plus higher-level project-level maps including author
aliasing~\cite{fry2020dataset} and a project-deforking
map~\cite{mockus2020complete}. We use the project-to-license (P2L)
map~\cite{jahanshahi2024license} for license events with timestamps
and the deforked-project map to avoid fork/duplicate bias. The term
\emph{project} refers to a deforked project throughout.

\subsection{License Change}

A within-project license change constitutes a deliberate event:
unlike the initial choice, which can be arbitrary, a switch reflects
strategic intent~\cite{kechagia2010open}, and the within-project
design implicitly controls for stable project characteristics. Because
the data are observational, we interpret findings as associations.

To investigate license switching, we select projects with more than
one license type in their lifetime and exactly one license type at
both first adoption and the latest state.

This also means that if a project starts with license A, then changes to B,
and later changes to license C, we consider it as one change from A to C,
rather than two separate changes.
Consequently, we excluded projects where the first license type and
the latest license type were the same.
Although these projects had other licenses at some point, they were
removed, resulting in no change between the first and last license types.

\begin{comment}
A subtle case arises when the comparison interval immediately following
the first license A overlaps with a short-lived intermediate license B
before the project settles on C. Inspecting the data, we find that this
applies to 1,462 out of 23,619 projects (approximately 6.2\% of the
regression sample). As a robustness check, we re-estimated the full
regression model after excluding these projects. All key findings remained
consistent in direction and significance, including the language-specific
patterns reported in the results section (e.g., positive associations between
permissive licenses and activity in Python, and negative associations in C/C++).
\end{comment}

Next, we categorize licenses into two high-level groups: ``permissive'', which 
includes public-domain and permissive licenses, and ``restrictive'', encompassing 
copyleft, weak-copyleft, and conditional open licenses.
Within these groups, we select projects that switched from a permissive to a 
restrictive license or vice versa.

To measure performance changes, we compute key project metrics during two separate 
one-year intervals: one immediately following the first license adoption and 
another immediately following the last license adoption.
Projects are excluded if less than one year separates the adoption dates of the
first and last licenses or if less than one year has elapsed since the last 
license adoption at the time of our data curation. 
To verify that results are not an artifact of this baseline window, we additionally
re-estimate the model using the year \emph{before} the last license adoption as the
pre-switch interval in place of the year following the first adoption.
The seven response metrics are the changes in the number of authors, blobs,
commits, files, active months, and upstream and downstream project counts.
We model the change in each metric (i.e., metric values in the post-switch 
interval minus those in the pre-switch interval) based on the direction of the 
license change (restrictive to permissive or permissive to restrictive).
We control for the project's primary language, its start and 
end times, the delay before the first license adoption, the elapsed time between
the first and last license adoptions, the proportion of new OSS projects 
adopting that license type at the time of the last license change, and the
project's pre-treatment popularity, measured as the number of upstream and
downstream projects in the year following the first license adoption.

To test our hypotheses, we selected a regression model appropriate to the 
nature of our response variable, specifically, multivariate multiple regression.
This model is an extension of multiple 
regression that allows for multiple dependent variables (outcomes) to be predicted
by multiple independent variables (predictors) simultaneously.
This model is useful when the dependent variables are correlated and need to be 
analyzed together to improve prediction accuracy and interpretation.
All count- and duration-valued response and control variables are log-transformed
as $\mathrm{sign}(x)\cdot\log(1+|x|)$ before entering the model to reduce skew;
the descriptive statistics report untransformed values for interpretability.
